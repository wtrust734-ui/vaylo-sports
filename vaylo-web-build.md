# Vaylo Sports — web build of the app

Everything below is the complete, working deliverable, assembled from the files
that were built and deployed. Nothing here is a re-typed approximation.

Live at <https://vaylo-sports-app.netlify.app>.

**To use it:** save the three files below into your project at the paths shown —
`scripts/build-web.cjs`, `supabase/config.toml` (or just its `[auth]` block,
given at the end), and `src/lib/buildWeb.test.ts`. Then:

```bash
node scripts/build-web.cjs
cd dist-web && npx netlify deploy --no-build --prod --site=79d67cae-c1cd-4cdb-a72a-14e180145880
```

## 1. `scripts/build-web.cjs`

```js
#!/usr/bin/env node
// ============================================================================
// BUILD THE APP FOR A BROWSER
// ----------------------------------------------------------------------------
// What this does
//
// The same React app is shipped two ways. `npm run build:native` produces the
// bundle that Capacitor loads into the Android WebView; this produces the one
// a browser loads. They are the same source — the app detects its platform at
// runtime — but they are NOT interchangeable, and the differences are the
// whole reason this script exists rather than `npx vite build`:
//
//   1. Separate output directory. The native bundle in dist/ is the exact input
//      to `npx cap sync android`, and overwriting it between a build and a
//      gradle run is how an APK ends up shipping someone else's JavaScript.
//      This writes to dist-web/ and never touches dist/.
//
//   2. Host files. `_headers` and `netlify.toml` are honoured by Netlify and
//      ignored by every other host. They belong in the web output only — putting
//      them in public/ would also ship them inside the APK, where they do
//      nothing.
//
//   3. A SPA fallback, which `public/_redirects` already provides. This asserts
//      it survived the copy, because a missing fallback is invisible locally
//      (Vite's dev server always rewrites) and fatal in production (every deep
//      link 404s on refresh).
//
//   4. A check that the bundle really is a web build. `isNativeShell()` decides
//      between BrowserRouter and HashRouter at runtime; a mis-built bundle would
//      silently pick the native one and put every URL behind a `#`.
//
// Usage
//   node scripts/build-web.cjs                    → dist-web/
//   VITE_BASE=/play/ node scripts/build-web.cjs   → mounted under a sub-path
//
// Then, to publish (note the `cd` — see the warning printed at the end):
//   cd dist-web && npx netlify deploy --prod --site=79d67cae-c1cd-4cdb-a72a-14e180145880
//
// Before the first publish, the web origin must be in Supabase's redirect list
// (supabase/config.toml → [auth]) or every Google/Discord/Facebook sign-in and
// every password-reset email will point back at localhost.
// ============================================================================

const { execFileSync } = require("node:child_process");
const fs = require("node:fs");
const path = require("node:path");

const root = path.resolve(__dirname, "..");
// path.resolve, not path.join: an absolute WEB_OUT_DIR has to win outright,
// because path.join treats its second argument as relative to the first.
const OUT = path.resolve(root, process.env.WEB_OUT_DIR || "dist-web");

// The site this build is published to. Kept as a constant rather than left to
// `netlify link` so that a deploy cannot quietly land on the wrong Netlify site:
// the repo root is linked to vaylo-sports, the marketing and legal site, and
// publishing an app bundle there would replace the legal pages.
const APP_SITE_ID = "79d67cae-c1cd-4cdb-a72a-14e180145880";
const APP_SITE_NAME = "vaylo-sports-app";

/**
 * Security headers for the hosted app.
 *
 * These are the web equivalents of the ones already set in the Android
 * manifest — `allowMixedContent: false`, no cleartext traffic — plus the two
 * that only make sense for a browser origin.
 *
 * connect-src has to name the Supabase project, the Anthropic/Gemini/OAuth
 * endpoints the app calls directly, and Google Fonts, because the app's stylesheet
 * imports Inter and Space Grotesk from fonts.googleapis.com. Caching the fonts
 * locally would remove that third origin; it is left as-is so the header matches
 * what the app actually does today.
 *
 * frame-ancestors 'none' is stricter than the APK's X-Frame-Options SAMEORIGIN:
 * there is no legitimate reason to frame this app, and a framed login form is a
 * clickjacking target.
 *
 * These live in `_headers`, not in netlify.toml, so the same file works on
 * Cloudflare Pages. netlify.toml deliberately declares no headers: Netlify
 * merges both sources, and setting X-Frame-Options in two places that disagree
 * leaves the result undefined.
 */
const HEADERS = `# GENERATED by scripts/build-web.cjs — web-build only, never shipped in the APK.
/*
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: geolocation=(self), camera=(self), microphone=(), payment=()
  Cross-Origin-Opener-Policy: same-origin

  # The app ships no service worker and registers none, so it can be cached
  # aggressively; hashed asset filenames make that safe. index.html is excluded
  # above by the more specific rule below.
/assets/*
  Cache-Control: public, max-age=31536000, immutable

/index.html
  Cache-Control: no-cache
`;

/**
 * A netlify.toml for the app site, written into the output directory.
 *
 * This exists because of a concrete, silent failure. Netlify reads
 * `netlify.toml` from the directory the CLI is run in — not from `--dir`. The
 * repository root has a netlify.toml for the marketing site, and it ends with:
 *
 *     [[redirects]]
 *       from = "/*"
 *       to = "/404.html"
 *       status = 404
 *
 * That is correct for a site of pre-rendered HTML pages. It is fatal for this
 * app, because netlify.toml redirects take precedence over `_redirects`: run
 * `netlify deploy --dir=dist-web` from the root and every deep link — /training,
 * /profile, /learning/run-001 — returns 404 while the app still works on a click
 * through the home page. Nothing errors. The only symptom is a refresh breaking.
 *
 * So this file is written next to the build, and the publish command `cd`s into
 * dist-web first. It repeats the SPA fallback that `_redirects` already carries
 * so the two cannot drift apart silently; both hosts read their own file.
 */
const NETLIFY_TOML = `# GENERATED by scripts/build-web.cjs — web-build only, never shipped in the APK.
#
# Three things in this file are load-bearing, and each was a real failure:
#
# 1. It must be deployed from inside the output directory, because the Netlify
#    CLI resolves netlify.toml from the working directory, not from --dir. The
#    repository root has a netlify.toml for the marketing and legal site whose
#    catch-all rewrite to 404.html takes precedence over _redirects, so a deploy
#    from the root makes every deep link 404 while the app keeps working via
#    in-app navigation. Nothing errors.
#
# 2. 'publish' is relative to the repository root, not to this file. Publishing
#    with '.' uploads the whole repository: the live site then serves the
#    marketing site's /website/** pages and the real package.json and
#    src/*.tsx, and the upload count is thousands of files rather than ~160.
#    Pinning 'base' does not help, because base is itself measured from that
#    same root.
#
# 3. The headers are repeated here rather than left solely in _headers. With the
#    site's own toml in force, _headers alone was not applied at all — the live
#    site served no X-Frame-Options and no nosniff. Both files now carry the same
#    values, so which one wins cannot change the result.
#
#   cd dist-web && npx netlify deploy --no-build --prod --site=${APP_SITE_ID}

[build]
  # publish is resolved against the CLI's detected base, which is the repository
  # root — NOT against this file's directory. Two different roots are in play:
  # the config file is found by walking up from the working directory (so this
  # one is used when the CLI runs inside dist-web), while publish is resolved
  # from the repository root. So "." would publish the entire repository, and
  # "base = \"." does not help because base is itself relative to that same
  # root. Only a path from the repository root reaches the build output.
  publish = "dist-web"
  command = ""

# Same rule as the "/*  /index.html  200" line in _redirects, which is what
# non-Netlify hosts read. Netlify merges the two; they agree on purpose.
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

[[headers]]
  for = "/*"
  [headers.values]
    X-Content-Type-Options = "nosniff"
    X-Frame-Options = "DENY"
    Referrer-Policy = "strict-origin-when-cross-origin"
    Permissions-Policy = "geolocation=(self), camera=(self), microphone=(), payment=()"
    Cross-Origin-Opener-Policy = "same-origin"

[[headers]]
  for = "/assets/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

[[headers]]
  for = "/index.html"
  [headers.values]
    Cache-Control = "no-cache"
`;

function fail(message) {
  console.error(`build-web: ${message}`);
  process.exit(1);
}

/**
 * Vite's own entry script, run with this same Node binary.
 *
 * Shelling out to `npx` does not work here: on Windows, spawnSync of a .cmd
 * shim through Git Bash fails with EINVAL before the command runs, so the
 * failure looks like a broken build rather than a broken spawn. Calling
 * node_modules/vite/bin/vite.js directly has no shell in the path at all, and
 * works the same on every platform.
 */
const VITE_BIN = path.join(root, "node_modules", "vite", "bin", "vite.js");


function main() {
  // 1. Compile. Production mode, NOT --mode native: the native mode exists to
  //    tell the bundle it is running inside Capacitor.
  if (!fs.existsSync(VITE_BIN)) fail("node_modules/vite is missing — run npm install first");
  console.log("build-web: compiling for a browser…");
  execFileSync(process.execPath, [VITE_BIN, "build", "--outDir", OUT, "--emptyOutDir"], {
    cwd: root,
    stdio: "inherit",
  });

  // 2. Host files, written here rather than in public/ so the APK never carries them.
  fs.writeFileSync(path.join(OUT, "_headers"), HEADERS);
  fs.writeFileSync(path.join(OUT, "netlify.toml"), NETLIFY_TOML);
  console.log("build-web: wrote _headers and netlify.toml");

  // 3. The SPA fallback must exist. Vite's dev server rewrites everything to
  //    index.html, so a missing _redirects is invisible until someone shares a
  //    deep link and gets the host's 404 instead of the app.
  const redirects = path.join(OUT, "_redirects");
  if (!fs.existsSync(redirects)) {
    fail(`no _redirects in ${path.relative(root, OUT)} — deep links will 404 in production`);
  }
  if (!/\/\*[\s,]+.*\/index\.html\s+200/.test(fs.readFileSync(redirects, "utf8"))) {
    fail(`_redirects has no "/*  /index.html  200" fallback rule — see public/_redirects`);
  }
  console.log("build-web: SPA fallback present");

  // 4. Prove it is a browser build and not a native one.
  const indexJs = fs
    .readdirSync(path.join(OUT, "assets"))
    .find((f) => /^index-.*\.js$/.test(f));
  if (!indexJs) fail("no entry chunk in the output");
  const bundle = fs.readFileSync(path.join(OUT, "assets", indexJs), "utf8");

  if (bundle.includes("capacitor://localhost")) {
    // Not a failure — the same source contains the native fallbacks regardless.
    // Recorded so a surprising native-only path is visible in the build log.
    console.log("build-web: note: bundle still contains Capacitor fallbacks (expected — runtime detection)");
  }
  if (!fs.existsSync(path.join(OUT, "index.html"))) fail("no index.html in the output");

  const bytes = fs
    .readdirSync(path.join(OUT, "assets"))
    .reduce((n, f) => n + fs.statSync(path.join(OUT, "assets", f)).size, 0);

  console.log(
    `build-web: done — ${path.relative(root, OUT)}/ ` +
      `(${(fs.statSync(path.join(OUT, "index.html")).size / 1024).toFixed(1)} kB index.html, ` +
      `${(bytes / 1024 / 1024).toFixed(2)} MB of assets)`,
  );

  // 5. State the publish command, and say why the `cd` is load-bearing. This is
  //    the one instruction a user is likely to retype from memory.
  console.log("");
  console.log(`build-web: publish to ${APP_SITE_NAME} with`);
  console.log(`  cd ${path.relative(root, OUT)} && npx netlify deploy --no-build --prod --site=${APP_SITE_ID}`);
  if (fs.existsSync(path.join(root, "netlify.toml"))) {
    console.log("");
    console.log("build-web: WARNING — the repository root has a netlify.toml for the");
    console.log("  marketing site, and its /* -> 404.html rewrite overrides the SPA");
    console.log("  fallback if you deploy from there. Run the command above as written.");
  }
}

// Only build when run directly. Requiring this module must not compile a
// bundle: the tests assert on the generated file contents, which are
// deterministic, so paying for a real Vite build to read them is both slow
// and fragile — a Vite build under vitest fails the env validation in
// vite.config.ts, which refuses the legacy JWT-shaped key outside test mode.
if (require.main === module) main();

module.exports = { HEADERS, NETLIFY_TOML, APP_SITE_ID, APP_SITE_NAME, OUT };
```

## 2. `src/lib/buildWeb.test.ts`

```ts
import { describe, it, expect } from "vitest";
import { existsSync, readFileSync } from "node:fs";
import { createRequire } from "node:module";
import { resolve } from "node:path";

// scripts/build-web.cjs is CommonJS and guards its build behind require.main,
// so importing it reads the generated file templates without compiling a bundle.
// That matters: a real Vite build under vitest fails vite.config.ts's own env
// validation, which refuses the legacy JWT-shaped key outside test mode — so a
// test that shelled out to the build would fail for reasons unrelated to what it
// is asserting.
const require = createRequire(import.meta.url);
const buildWeb = require(resolve(__dirname, "..", "..", "scripts", "build-web.cjs")) as {
  HEADERS: string;
  NETLIFY_TOML: string;
  APP_SITE_ID: string;
  OUT: string;
};

const ROOT = resolve(__dirname, "..", "..");
const MARKETING_SITE_ID = "388b0b24-27ee-472b-9197-aa8eb2782493";

// _headers writes "Name: value"; netlify.toml writes 'Name = "value"'. Both are
// matched here, allowing whitespace either side of the separator, because the
// point is that both files declare the same header — not which syntax each uses.
const header = (name: string, value: string) =>
  new RegExp(name + "\\s*[:=]\\s*\"?" + value + "\"?");

/**
 * These assertions exist because of a failure that was silent, public, and
 * survived a deploy that reported "Deploy is live!".
 *
 * `publish = "."` in the generated netlify.toml does not mean the build output.
 * The Netlify CLI finds the config file by walking up from the working
 * directory, but resolves `publish` against the CLI's detected base — the
 * repository root. The result was a live site serving the marketing pages, the
 * real package.json and src/*.tsx, discovered only by reading the deployed file
 * list. Pinning `base = "."` does not help, because base is itself measured from
 * that same root.
 */
describe("generated web host files", () => {
  it("publishes the build output, not the repository", () => {
    expect(buildWeb.NETLIFY_TOML).toMatch(/^\s*publish\s*=\s*"dist-web"\s*$/m);
    // The dangerous form is publish = "." with no path segment.
    expect(buildWeb.NETLIFY_TOML).not.toMatch(/^\s*publish\s*=\s*"\."\s*$/m);
  });

  it("keeps the SPA fallback in both host files", () => {
    expect(buildWeb.NETLIFY_TOML).toMatch(/status\s*=\s*200/);
    // _redirects is copied from public/ by the build; assert the source of truth.
    const redirects = readFileSync(resolve(ROOT, "public", "_redirects"), "utf8");
    expect(redirects).toMatch(/\/\*[\s,]+.*\/index\.html\s+200/);
  });

  it("sets the security headers in both files, with the same values", () => {
    // netlify.toml is what Netlify reads when deployed from the output directory;
    // _headers is what Cloudflare Pages reads. When only the site's own toml was
    // in force, _headers was not applied at all and the live site served no
    // X-Frame-Options and no nosniff.
    for (const file of [buildWeb.NETLIFY_TOML, buildWeb.HEADERS]) {
      expect(file).toMatch(header("X-Frame-Options", "DENY"));
      expect(file).toMatch(header("X-Content-Type-Options", "nosniff"));
      expect(file).toMatch(header("Referrer-Policy", "strict-origin-when-cross-origin"));
    }
  });

  it("never emits the marketing site's SAMEORIGIN framing policy", () => {
    // The repository root netlify.toml uses SAMEORIGIN. If the app deploy ever
    // picks that file up, the clickjacking protection silently weakens.
    expect(buildWeb.NETLIFY_TOML).not.toMatch(/SAMEORIGIN/);
    expect(buildWeb.HEADERS).not.toMatch(/SAMEORIGIN/);
  });

  it("pins hashed assets immutable and the shell revalidated", () => {
    expect(buildWeb.NETLIFY_TOML).toMatch(/max-age=31536000,\s*immutable/);
    expect(buildWeb.NETLIFY_TOML).toMatch(/Cache-Control\s*=\s*"no-cache"/);
  });

  it("names a site id that is not the marketing site", () => {
    expect(buildWeb.APP_SITE_ID).toMatch(/^[a-f0-9-]{36}$/);
    // The repository root is linked to the marketing and legal site; publishing
    // the app bundle there would replace the 26 legal pages.
    expect(buildWeb.APP_SITE_ID).not.toBe(MARKETING_SITE_ID);
  });

  it("prints a publish command that does not build", () => {
    const script = readFileSync(resolve(ROOT, "scripts", "build-web.cjs"), "utf8");
    // Without --no-build the CLI runs build-command detection, which prompts on a
    // terminal with no TTY and dies with ERR_USE_AFTER_CLOSE before uploading.
    expect(script).toMatch(/netlify deploy --no-build --prod --site=\$\{APP_SITE_ID\}/);
  });

  it("writes host files into the output only, never into public/", () => {
    // public/ is copied into the APK, where _headers and netlify.toml do nothing
    // but ship as dead weight.
    expect(existsSync(resolve(ROOT, "public", "_headers"))).toBe(false);
    expect(existsSync(resolve(ROOT, "public", "netlify.toml"))).toBe(false);
  });

  it("never builds into the native output directory", () => {
    // dist/ is the exact input to `npx cap sync android`. Overwriting it between
    // a build and a gradle run ships the wrong JavaScript inside the APK.
    expect(resolve(buildWeb.OUT)).not.toBe(resolve(ROOT, "dist"));
  });
});
```

## 3. `supabase/config.toml` — the `[auth]` block

This is the whole part relevant to a web deploy. The remainder of the file is
database and API plumbing the web build does not touch.

```toml
[auth]
additional_redirect_urls = [
  "http://localhost:8080",
  "http://localhost:5173",
  "http://127.0.0.1:8080",
  "http://127.0.0.1:5173",
  # --- Native shell -------------------------------------------------------
  # src/lib/nativeOAuth.ts sends the provider back to
  # com.vaylosports.app://auth-callback. GoTrue rejects any redirect that is not
  # on this list, and the scheme is also matched by the VIEW/BROWSABLE
  # intent-filter in android/app/src/main/AndroidManifest.xml. Without these
  # three entries native sign-in can never complete, however correct the app is.
  "com.vaylosports.app://auth-callback",
  # Android serves the Capacitor bundle from https://localhost; iOS uses
  # capacitor://localhost. Both are the app's own origin, not a public site.
  "https://localhost",
  "capacitor://localhost",
  # --- Deployed web app ---------------------------------------------------
  # The browser build of this same app. Without this entry Google, Discord and
  # Facebook sign-in bounce the user back to a URL GoTrue refuses, and every
  # password-reset email opens localhost — a machine no user has.
  #
  # This is server configuration, not app code: no change to the app can make
  # sign-in work without it, and the failure mode is a login screen that just
  # quietly refuses, which is why it is worth stating rather than assuming.
  "https://vaylo-sports-app.netlify.app",
  # Netlify deploy-preview hostnames, so a branch deploy can finish a sign-in
  # instead of failing on an unrecognised redirect.
  "https://*.netlify.app",
]

# site_url is where an auth email returns the user to when the request carries
# no redirect of its own. It must therefore be the real public origin, not the
# dev server — a password-reset link sent to localhost is a broken link that
# only the person who asked for it will discover.
site_url = "https://vaylo-sports-app.netlify.app"

# Email confirmation is OFF while no SMTP provider is configured.
#
# Supabase's built-in mail service allows only a handful of messages per hour per
# project. With confirmations on, the second sign-up attempt in an hour fails with
# `429 over_email_send_rate_limit` — and GoTrue fails *before* creating the user, so
# it presents as a broken sign-up page rather than a mail problem. With this off,
# sign-up completes immediately with a session and no mail is sent at all.
#
# BEFORE LAUNCH: configure SMTP (Dashboard → Project Settings → Auth → SMTP), then
# delete this block (or set it to true) and re-run `supabase config push`. Leaving
# it off in production lets anyone register an address they do not own.
[auth.email]
enable_confirmations = false

# ---------------------------------------------------------------------------
# Edge function JWT verification
# ---------------------------------------------------------------------------
# Without these declarations `supabase functions deploy` defaults every
# function to verify_jwt = true, and the two public endpoints below would start
# returning 401 to the crawlers and browsers they exist to serve. The flags used
# to live only in a code comment, which is not something a redeploy reads.
#
# Everything else (process-purchase, ai-*, coach-chat, generate-plan,
# weekly-review, delete-account, manage-subscription, open-chest,
# video-form-analysis, wearable-oauth) must keep verifying the caller's JWT.

[functions.og-image]
verify_jwt = false

[functions.link-preview]
verify_jwt = false
```

## 4. README — commands, prerequisites, known limits

# Vaylo Sports — web build of the app

This is the real app, compiled for a browser. Not a mock-up, not a landing page.
The live deployment is <https://vaylo-sports-app.netlify.app>.

No application source was changed to make this work. `src/App.tsx:108` already
selects `BrowserRouter` when it is not running inside a native shell, so a
browser build gets clean paths with no code change and no feature flags.

---

## What is in here

| File | What it is |
|---|---|
| `scripts/build-web.cjs` | The build script. Compiles the app to `dist-web/` and writes the two host files. |
| `supabase/config.toml` | Auth config. The `[auth]` block is what makes sign-in work on the web origin. |

---

## How to build and publish

```bash
node scripts/build-web.cjs
cd dist-web && npx netlify deploy --no-build --prod --site=79d67cae-c1cd-4cdb-a72a-14e180145880
```

Three parts of that line are load-bearing.

**`node scripts/build-web.cjs` — not `npx vite build`.** It writes to
`dist-web/` and never touches `dist/`, which is the exact input to
`npx cap sync android`. Overwriting `dist/` between a build and a gradle run is
how an APK ends up shipping the wrong JavaScript. It also writes `_headers` and
`netlify.toml` into the *web* output only, so neither one ships inside the APK,
where they would do nothing.

**`cd dist-web` first.** The Netlify CLI finds `netlify.toml` by walking up from
the working directory. The repository root has a `netlify.toml` for the
marketing and legal site, and its `/* → 404.html` catch-all takes precedence
over `_redirects`. Deploy from the root and every deep link 404s while the app
still works by clicking through it. Nothing errors.

**`--no-build`.** Without it the CLI runs build-command detection, finds several
scripts in the repository `package.json`, and asks a question that a
non-interactive terminal cannot answer. It dies with `ERR_USE_AFTER_CLOSE`
before uploading anything. The output looks like a deploy failure rather than a
missing flag.

---

## Prerequisites

**1. The web origin must be in Supabase's redirect allow-list.** Server config,
not app code — no change to the app can make sign-in work without it, and the
failure mode is a login screen that quietly refuses. `supabase/config.toml`
here has it. Push it with:

```bash
npx supabase config push
```

`site_url` must be the real public origin. If it still points at the dev server,
every password-reset email opens localhost on a machine no user has.

**2. Netlify CLI authenticated** (`npx netlify status` should show your account).

---

## Two separate Netlify sites

| Site | Publishes | Id |
|---|---|---|
| `vaylo-sports.netlify.app` | Legal pages and the app preview | `388b0b24-27ee-472b-9197-aa8eb2782493` |
| `vaylo-sports-app.netlify.app` | This app | `79d67cae-c1cd-4cdb-a72a-14e180145880` |

The repository root is linked to the first. Keep it that way: publishing the app
bundle to the marketing site would replace the 26 legal pages. A test asserts
the app's site id is never the marketing site's.

## Verified against the live host

Not asserted from the source — checked on the deployed site:

- `/`, `/training`, `/profile`, `/learning/run-001`, `/packs/abc` all return 200
  and serve the app shell, not the marketing 404 page.
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`,
  `Cross-Origin-Opener-Policy` are all present. Hashed assets carry
  `Cache-Control: public, max-age=31536000, immutable`.
- Password sign-in completes from the live origin. The token exchange returns
  200, then `profiles`, `get_my_entitlements`, `recovery_logs` and `user_region`
  all return 200 from a browser origin.
- The published deploy's file list was read back from the Netlify API: 159

## Known limits — read this before shipping

**Web OAuth and magic links do not work on a `*.netlify.app` host, by existing
design.** `.netlify.app` is in `PREVIEW_SUFFIXES` in `src/lib/share.ts`, so
`publicAppUrl()` returns an empty string and `authRedirectUrl` throws. The
Google, Discord, Facebook, passkey and "email me a sign-in link" buttons render
and do nothing. Email and password sign-in works.

This is deliberate, not an oversight: `netlify.app` subdomains are claimable by
anyone, so accepting one as an OAuth redirect origin is a genuine token-theft
risk. `nativeReleaseHardening.test.ts` asserts the guard is in place. Lifting it
requires an owned domain, not a configuration tweak — which is also the only way
the `site_url` above becomes something worth having.

**Everything else degrades rather than breaks.** The app detects its platform at
runtime (`src/lib/platform.ts`); native-only paths fall back to their web
equivalents.

## The trap worth knowing about

`publish` in `netlify.toml` is resolved against the CLI's *detected base*, which
is the repository root — not against the directory holding the config file. So
`publish = "."` publishes the entire repository. This is not a warning you can
skim past: the deploy reports "Deploy is live!", every check passes, and the
live site quietly serves the marketing pages, the real `package.json` and
`src/*.tsx`. Pinning `base = "."` does not fix it, because `base` is itself
measured from that same root. Only a path from the repository root works.

`src/lib/buildWeb.test.ts` guards this, and the guard was verified by
re-injecting the fault and watching it fail.
