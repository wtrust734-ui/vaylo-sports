# Feature → legal process

**The rule: a feature is not finished until the legal pages describe it.**

This is the thing you asked for by name — *"if I ask you to add a new feature,
edit the legal pages to make sure that applies to that feature."* This document
makes that rule concrete, so it survives past whoever remembered it.

The reason it needs writing down: the Vaylo legal set is **generated from
`legal/` and asserted by tests**. Two consequences follow, and both are traps
worth naming before they bite.

---

## 1. Why a new feature usually means a legal change

A feature changes at least one of these, and each one is published somewhere:

| A feature changes… | So this document must move |
|---|---|
| what data is collected, or why | `legal/privacy.html`, and `legal/ai-data-use.html` if an AI provider sees it |
| what a device permission or sensor reads | `legal/privacy.html`, `legal/wearable-health-privacy.html` |
| what is generated by a model rather than calculated | `legal/ai-disclaimer.html`, `legal/ai-training-advice.html` |
| anything health, training-load or injury adjacent | `legal/health-safety.html`, `legal/injury-guidance.html`, `legal/nutrition-disclaimer.html`, `legal/mental-wellbeing.html` |
| anything a minor can reach, or is deliberately blocked from | `legal/child-safety.html` |
| anything bought, priced, earned or refunded | `legal/purchases.html`, `legal/refunds.html`, `legal/competition-terms.html` |
| anything social, shared, reported or blocked | `legal/community-guidelines.html`, `legal/report-content.html` |
| anything a brand pays for, or a sponsored surface | `legal/advertising.html` (§8 holds the sponsorship enquiry terms) |
| a new third party that processes anything | `legal/privacy.html` §third-parties, `legal/cookies.html` if it sets storage |
| a new cookie or any local storage | `legal/cookies.html` |

If none of those moved, say so out loud in the change description — *"no legal
surface changed, because…"*. Silence is the failure mode this document exists to
prevent.

## 2. The concrete mechanics

The legal documents are **authored once** and **published three ways**. Never
edit the published copies; they are overwritten.

```
legal/<slug>.html          ← author here (hand-written, self-contained)
legal/pages.json           ← register the slug (only for a NEW document)
legal/operator.json        ← the one place the operator name and email live

  ├─→ scripts/gen-legal-pages.cjs → supabase/functions/legal/pages.generated.ts
  │                                  (what the in-app legal library serves)
  └─→ scripts/gen-website.cjs     → website/legal/<slug>/index.html
                                     (what the website Legal Centre serves)
```

So, after editing a document:

```bash
node scripts/gen-legal-pages.cjs    # regenerate the in-app embedding
npm run site:build                  # regenerate the website
```

Then:

```bash
npx vitest run src/lib/legalPages.test.ts src/lib/legalContentConsistency.test.ts \
  src/lib/website.test.ts src/lib/legalHostLayout.test.ts src/lib/legalInApp.test.ts
```

### If you add a NEW document (rather than editing one)

A new slug means five places, and the tests will name each one if you miss it:

1. `legal/<slug>.html` — copy the structure of `legal/waitlist-terms.html`
   (inline `<style>`, `%%OPERATOR_NAME%%` / `%%CONTACT_EMAIL%%` placeholders, a
   `.toc`, and a closing `<nav class="nav">`).
2. `legal/pages.json` → both the `$topicMap` note and the `pages` map.
3. `site/data/site.mjs` → `LEGAL_DOCUMENTS` (title + one-line summary), and
   `FOOTER` if it belongs in the footer.
4. `src/lib/legalUrls.ts` → the `LegalSlug` union.
5. Regenerate (above) and run the tests.

Use **document-relative** links between documents (`href="privacy"`). The
generator rewrites them to the published path. A root-absolute link (`/legal/x/`)
works on the website and breaks inside the app, where the document is rendered in
an iframe with no such route — a test rejects the bare form for exactly this
reason.

## 3. Two writers, one truth

`legal/*.html` is the source for **both** consumers, and a test fails if the
committed embedding is stale. Never edit `website/legal/**` or
`supabase/functions/legal/pages.generated.ts` by hand: they are rebuild output,
and a hand edit is invisible until the next build silently replaces it.

## 4. Definition of done for any feature

- [ ] The feature's data, permission, AI, health, age, purchase or social
      surface has been matched against the table in §1.
- [ ] Every document that needed to move, moved.
- [ ] The version line and date at the top of each changed document were bumped.
- [ ] `node scripts/gen-legal-pages.cjs` ran.
- [ ] `npm run site:build` ran.
- [ ] The five legal test files pass.
- [ ] If the feature added a *claim* the product does not deliver yet, the claim
      says so in the document **and** on the page that advertises it — the
      `/sponsors/` questionnaire marking "AI preference" as *not implemented* is
      the pattern to copy.
- [ ] If nothing legal moved, the change description says why.

## 5. What is enforced automatically, and what relies on you

Enforced by tests today (so a machine will catch it):

- the published site and the in-app embedding match `legal/` exactly;
- every slug in `pages.json` is published on the website and linked from the
  Legal Centre;
- every slug in `legalUrls.ts` is linked from the in-app legal index;
- no unresolved `%%PLACEHOLDER%%` reaches a reader;
- no invented company particulars appear anywhere;
- a document's cross-links all resolve;
- the site's class coverage and security headers still hold.

**Not** enforced, and therefore your job:

- whether the *words* in a document are true of the product;
- whether a new feature needed a new document at all;
- whether a published claim has quietly stopped being true.

That last one is the real risk in this repository, because its published
documents are unusually specific. When a feature changes behaviour that a
document describes in the present tense, the document is wrong the moment the
feature ships — not the moment someone notices.
