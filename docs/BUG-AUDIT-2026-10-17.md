## 2. Findings

### P1-1 · `process-purchase`: one verified store token can grant an entire basket
[supabase/functions/process-purchase/index.ts:180-193](supabase/functions/process-purchase/index.ts#L180) verifies **one** Play purchase and only cross-checks that the verified product id is *somewhere in the basket* (`basketIds.includes(verifiedProductId)`). The grant loop then processes **every** item; the per-item money check (`priceCents > 0 && PAYMENT_MODE !== "store"` ~L368) passes once store mode is on. A browser-supplied `items` array of `[cheap_pack, expensive_pack]` with one token for `cheap_pack` gets both grants.
**Gated:** today's deployment runs `PAYMENT_MODE=test/free`, where the honest refusal (503) covers this path; the bug activates **the moment store billing goes live** (`STORE_BILLING_ENABLED`, §7.1 of the cosmetics proposal). One-line fix: require verified product id on *every* money item, or bind the token to exactly one grant (the `transactionReference` already keys only the first item — extend that idea).

### P1-2 · `process-purchase`: credit-pack grant failure leaves paid-but-unpaid state and blocks the retry
The insert of `user_purchases` happens **per item**, then a single shared `credits_grant` runs at the end (~L600). Coin and feature paths each roll back their own row on failure (`rollBackPurchase`), but the credit-pack **and** infinite-unlimited paths return 500 **without rolling back their inserted purchase rows**. A retry with the same store reference then hits the duplicate pre-check (~L292, `provider_reference` match → 409 "already applied") — the athlete was charged and never granted. The `credits_grant` idempotency key would have made a retry safe; the pre-check prevents it from ever running.
**Gated:** same store-mode rollout as P1-1; partially live now (`test` mode path shares the insert-then-grant sequence). Fix: on `credits_grant`/`grant_infinite_credits` failure, delete the inserted rows (as the other branches already do) or reorder (grant first idempotently, then record).

### P1-3 · Launch-gate violation: `pipelineDashboard` flag defaults to ON
[featureFlags.ts:100](src/config/featureFlags.ts#L100) `envOverride("pipelineDashboard", true)` — the suite's launch-contract test (`defaults every not-yet-ready flag to off`) fails against it. Either the flip was intentional (then the test, which is the guardrail, must be updated *and* the launch checklist re-examined) or the default was flipped accidentally while the screen behind it is still type-broken (P2-1). Unverifiable intent from code alone → decision needed.

### P2-1 · `/pipeline` admin screen: types are stale and the file carries real bugs
[PipelineDashboard.tsx](src/components/pipeline/PipelineDashboard.tsx) (38 type errors). The `pipeline_jobs`/`pipeline_chat` tables **do exist** (migration `20261016200000`) — so most errors show [types.ts](src/integrations/supabase/types.ts) is stale (generated before the migration) and blocks typecheck repo-wide. Mixed in are real defects the stale types mask: `.select("stage", "owner_id")` invalid args (should be `{ stage: true, owner_id: true }`), `supabase.auth.user` (removed in v2 — every auth call here fails at runtime), `job.human_input` vs `humanInput` (property miss at L641/643 → the human-input banner silently renders nothing), and an icon *component* rendered as text at L472. Fix path: `supabase gen types`, then fix the 3-4 genuine defects. No release impact while the feature is a behind-flag admin screen — but it fails visibly if the flag flip (P1-3) is intentional.

### P2-2 · Client-side overlay-state regression test fails → website/clone source lag
[healthConnectEntry.test.ts:158](src/lib/healthConnectEntry.test.ts#L158) expects the one-line form `<HealthConnectPrompt open={showHealthConnect}` but [Profile.tsx:879-881](src/pages/Profile.tsx#L879) renders it multiline — the feature **works** (verified: state, trigger at L433, render at L879); the source-pinning test is brittle to formatting. Same class: `overflowLayout.test.ts` header test (`manus-skill-skeleton.ts`) sits in the app tree but is excluded from app tsconfig. These failures are tests out of sync, not user-facing bugs — except P2-3.

### P2-3 · Collection page: mobile overflow on the Bundles grid (user-visible)
[Collection.tsx:378](src/pages/Collection.tsx#L378) `className="grid gap-3 sm:grid-cols-2 lg:grid-cols-3"` — no base `grid-cols-*`, so mobile gets an auto track sized to max-content; the guard test (`overflowLayout.test.ts`) explicitly fails on it. Symptom: horizontal scroll/clipped bundle cards on narrow phones on the *Cosmetics tab's bundles rail*. Fix: `grid grid-cols-1 gap-3 sm:grid-cols-2 …`.

### P2-4 · `open-chest` race is check-then-mutate-then-record
[open-chest/index.ts](supabase/functions/open-chest/index.ts) reads the prior claim (L44), rewards, then inserts the claim LAST (L158) with no use of a unique-constraint error path. Two concurrent calls both mutate before one loses the insert. **Downgraded by DB constraints [verified]:** `user_rewards` has `UNIQUE(user_id, reward_id)` and `credits_grant` has an idempotency key — so duplicate grants collapse and the loser's request 500s without having duplicated value. Residual: a wasted roll + spurious 500; no money impact. Fix when convenient: insert the claim row FIRST with ON CONFLICT DO NOTHING and treat row-count-0 as the gate.

### P2-5 · Age gates are self-reported by design — flag for release decision, not a code bug
[age.ts](src/lib/age.ts) states "`We don't verify age`" and `dietPlanRefusalReason` consumes the self-reported DOB; server authorization accordingly trusts an editable DOB. Under the research in the cosmetics proposal (COPPA/GDPR-K), this is a *policy decision to ratify* in writing (or add age assurance), not a defect to silently leave in the "fine" column. Include in the same review as the photo-AI consent works.

## 3. What was audited and found healthy (so it isn't re-suspected)

- **Live DB posture [verified against the real project]:** all 31 security checks pass — RLS probes, message integrity, ownership RPCs, friend-scoping, no client minting of coins/credits.
- **Money math & idempotency design mostly sound** (money-mirror tests + coin/credit ladders + the unique `provider_reference` index on `user_purchases`), the above P1s being the perimeter exceptions.
- Local-day arithmetic ([dates.ts](src/lib/dates.ts)) is exemplary: explicit non-UTC day keys, canonical `daysBetween`, server-side ±1-day clamping on the streak RPC.
- Offline write queue ([offlineQueue.ts](src/lib/offlineQueue.ts)): client-PK idempotent replay, network-vs-rejected distinction, bounded queue, scoped rollback — built right.
- Secrets: scan clean in 1110 files.
